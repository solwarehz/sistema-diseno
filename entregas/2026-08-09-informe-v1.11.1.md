## 1 · Cómo actualizar

```bash
npm install "github:solwarehz/sistema-diseno#v1.11.1"
```

**Usen la etiqueta.** Sin ella npm instala `main`, que hoy tiene esta misma
versión pero avanzará: quedarían atados a «lo último», y una actualización que
no decidieron ustedes puede entrar en un despliegue sin que nadie la revise.

**No usen rangos** (`^1.11.0`): npm no los resuelve en dependencias de GitHub, y
creerían estar en una versión distinta de la real.

Comprueben qué quedó instalado:

```bash
node -p "require('sistema-diseno-ae/package.json').version"   # 1.11.0
```

Si sale `404` o `repository not found`, no es el comando: es acceso al
repositorio, que es privado. Pídanlo.

### El repositorio y el paquete no se llaman igual

No es un error. **Se instala desde el repositorio y se importa por el nombre del
paquete**; npm resuelve el segundo leyendo el `package.json` del primero.

| | |
|---|---|
| Repositorio | `solwarehz/sistema-diseno` |
| Paquete | `sistema-diseno-ae` |

### Configuración del empaquetador — **esto no se puede saltar**

Los componentes viajan como `.tsx` **sin compilar**. Decíamos que «Next y Vite lo
entienden»: lo entienden en el código del proyecto, **no dentro de
`node_modules`**, que es donde va a estar esto. Era un fallo de nuestra
documentación y costó una tarde a quien se lo encontró.

**Next**

```js
// next.config.mjs
const nextConfig = { transpilePackages: ['sistema-diseno-ae'] };
export default nextConfig;
```

**Vite**

```js
// vite.config.ts
export default defineConfig({
  optimizeDeps: { exclude: ['sistema-diseno-ae'] },
});
```

**Webpack** — la regla de TS suele excluir `node_modules`; hay que dejar pasar
este paquete:

```js
{ test: /\.tsx?$/, include: [/src/, /node_modules\/sistema-diseno-ae/], use: 'ts-loader' }
```

Si su proyecto no compila TypeScript, usen `componentes.css` con el marcado de
`comportamiento.md`. Todo funciona igual; lo que no tendrán es el
comportamiento.

## 2 · Cómo se usa

```jsx
import 'sistema-diseno-ae/tokens.css';       // SIEMPRE primero
import 'sistema-diseno-ae/componentes.css';  // después: usa esas variables

import { TablaDatos, Boton, Chip, Campo, SelectorBusqueda } from 'sistema-diseno-ae/componentes';
```

El orden de los dos `import` de CSS no es estilo: `componentes.css` usa las
variables que declara `tokens.css`. Al revés, no hay ningún color definido.

Catorce componentes. Lo que ya no escriben ustedes:

| Componente | Lo que resuelve |
|---|---|
| `TablaDatos` | Ordenar, filtrar, paginar, elegir columnas, plegar filtros conservando valores |
| `RangoFecha` | El calendario completo por teclado, el anuncio del cambio de mes, el foco |
| `SelectorBusqueda` | El patrón `combobox` de ARIA entero. Sin umbral: si busca, busca siempre |
| `Confirmacion` | El foco en la opción segura y su devolución al cerrar |
| `Horario` | Ejes rotables, 12/24 h, preferencia recordada |
| `Boton` | **Impide el doble envío solo** — ver abajo |
| `Campo` `Chip` `Avatar` `Interruptor` `Paginacion` `Tarjeta` `Enlace` `Estados` | Anillo de foco, estados, etiqueta vinculada, tamaño táctil |

**Los componentes se componen entre ellos.** `TablaDatos` importa `Boton`,
`Chip`, `Campo` y `Paginacion` en vez de rehacerlos: cuando el botón mejore, el
de dentro de la tabla mejora con él. Si tenían un parche para el botón de la
tabla, pueden quitarlo.

## 3 · Lo nuevo de esta versión

### El botón impide el doble envío por sí mismo

Si `onClick` devuelve una promesa, el botón se deshabilita, gira, marca
`aria-busy` y se libera al terminar — **resuelva o falle**. Y descarta los clics
que lleguen mientras tanto.

```jsx
<Boton variante="principal" onClick={() => fetch('/api/guardar', {…})}>
  Guardar
</Boton>
```

**No hay que poner nada.** Se resolvió dentro de `Boton` y no en un componente
aparte a propósito: un `BotonServidor` separado sería una garantía de la que se
puede salir eligiendo el otro botón, y el día que alguien pone el botón normal
en «Guardar», el doble envío vuelve.

Cubre el caso real, que no es el descuido: se pulsa dos veces **porque el
servidor tarda y la persona insiste**. Entre pulsar y repintar caben dos clics.

Si su acción no devuelve promesa, pasen `ocupado` a mano.

### La confirmación arranca el foco en «Cancelar»

**Esto cambia el comportamiento anterior.** Antes el foco entraba en el botón
que confirma — en una confirmación destructiva, el que borra. Un Enter por
costumbre, la misma tecla que se acababa de pulsar para llegar ahí, ejecutaba lo
irreversible.

Ahora arranca en la opción segura. Quien necesite lo contrario:

```jsx
<Confirmacion focoInicial="accion" … />
```

Lo reportó Control Administrativos V2.0, que ya lo hacía así en su producto.

### La tabla tiene modo servidor

Ordenar en el navegador con paginación de servidor ordena **solo la página
visible**: el resultado parece ordenado y no lo está.

```jsx
<TablaDatos
  modo="servidor"        // la tabla no toca los datos
  total={380}            // obligatorio: cuántas hay EN TOTAL
  filas={paginaActual}   // lo recibido ES la página
  columnasFijas={['documento']}
  alCambiar={(estado) => consultar(estado)}
/>
```

`alCambiar` les entrega `{ orden, filtros, pagina, porPagina }` y **la consulta
la arman ustedes**: el sistema no impone nombres de parámetros, porque el día
que decidiera cómo se llama su API dejaría de servir para el siguiente producto.

`columnasFijas` marca las columnas que el selector no puede quitar. Una tabla sin
la columna que identifica cada fila no identifica nada.

Y por columna: `ordenable: false` y `filtrable: false` cuando el control
engañaría. Esto ya existía desde antes.

## 4 · Los colores: la regla, sin excepciones

**Ningún color se crea fuera del sistema de diseño.** Ni en su proyecto, ni en
el nuestro por petición suya.

Hay **114 colores autorizados**, congelados, y **9 conocidos pero prohibidos**
—la familia `marca`—. La diferencia importa:

- **Autorizado** — puede vivir en el sistema. Se nombra `familia_paso`:
  `azul_600`, `ambar_900`, `negro_1000`.
- **Conocido y no autorizado** — está nombrado **para poder bloquearlo**: lo que
  no tiene nombre no se puede vigilar.

Dentro de un componente **no usen ni el escalón ni el hexadecimal**: usen el
**token semántico**, que es el que está medido contra un fondo concreto.

```jsx
// NO — la primitiva no sabe sobre qué fondo la van a poner
<div className="bg-[#0063CB]">

// SÍ
<div className="bg-accion">
```

Si necesitan un tono que no existe, **se pide y se mide**. No existe la salida de
escribirlo a mano «solo esta vez»: un color literal no pasa por ningún par
verificado, así que su contraste no lo comprueba nadie y sale en verde mientras
la pantalla incumple.

Ampliar la lista de autorizados no lo decide el equipo de diseño: lo decide el
responsable, caso por caso.

## 5 · Lo que se rompe al subir desde la v1.7.0

| Antes | Ahora | Por qué |
|---|---|---|
| `.av-` en el avatar | `.avatar-` | Chocaba con el aviso temporal y heredaba su relleno |
| El interruptor usaba `error-*` | `apagado-fondo` `apagado-borde` `apagado-bolita` | «Apagado» es una elección, no un fallo |
| `--sombra-capa` sin declarar | Viene en `componentes.css` | No llegaba: la capa flotante y el menú salían planos |
| `Confirmacion` enfocaba la acción | Enfoca «Cancelar» | Ver §3 |

Y una corrección visible: **el aviso temporal ahora lleva fondo teñido** además
del filete. Antes era una tarjeta blanca con una raya de color, que no era lo que
la documentación describía.

## 7 · Qué hacer si les falta algo

**No lo construyan en su proyecto.** Eso deja al sistema sin enterarse y al
siguiente proyecto reconstruyéndolo. Manden el requerimiento y se decide si es
del sistema o suyo.

Los criterios están en `sistema/componentes/POLITICA-DE-CREACION.md`, que viaja
en la entrega. En corto: **si lo pide un segundo proyecto es del sistema; si solo
tiene sentido en el suyo, es suyo.**

Lo que sí es suyo y el sistema no va a decidir: qué datos muestran, qué permisos
tiene cada rol, las reglas de validación de su dominio y qué pantallas existen.
